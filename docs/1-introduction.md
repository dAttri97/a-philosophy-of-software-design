# Chapter 1 Introduction
(It’s all about complexity)

Writing computer software is one of the purest creative activities in human history. Programmers are not constrained by physical laws; we can build exciting virtual worlds with behaviors that could never exist in the real world. Programming is not like ballet or basketball, which demand great physical talent and coordination. Programming requires a creative mind and organized thinking. If you can imagine a system, you can probably implement it in a computer program.

This means the greatest limit on writing software is our ability to understand the systems we create. As programs evolve and gain features, they grow more complex because of subtle dependencies among components. Over time, complexity accumulates, and it becomes harder for programmers to keep all the relevant factors in mind when changing the system. That slows development and causes bugs, which slow development further and raise cost. Complexity increases inevitably over the lifetime of any program. The larger the program and the more people involved, the harder complexity is to manage.

Good development tools help us cope with complexity, and many excellent tools have been created over the last few decades. But there is a limit to what tools alone can do. If we want writing software to become easier so we can build larger, more powerful systems more cheaply, we must find ways to simplify software. Despite our best efforts, complexity still grows over time, but simpler designs let us build bigger, more capable systems before complexity becomes overwhelming.

There are two general ways to tackle complexity, both discussed in this book. The first is to remove complexity by making code simpler and more obvious—for example, by eliminating special cases or using a consistent representation.

The second way to address complexity is to encapsulate it so that programmers working on one part of a system do not have to face all of its complexity at once. This approach is called *modular design*. In modular design, a software system is divided into modules, such as classes in object-oriented languages. Modules are designed to be relatively independent so a programmer can work on one module without needing deep knowledge of others.

Because software is highly malleable, software design is a continuous process throughout the system’s entire lifecycle—unlike the design of physical systems such as buildings, ships, or bridges. Yet software design is not always taken seriously. For much of programming’s history, design was concentrated at the beginning of a project, like other engineering disciplines. That extreme approach is the waterfall model: the project is split into separate phases such as requirements definition, design, coding, testing, and maintenance. In the waterfall model each phase must finish before the next begins, often with different people responsible for each phase. The entire system is designed in one design phase. At the end of that phase the design is frozen; later phases flesh out and implement it.

Unfortunately the waterfall model rarely fits software well. Software systems are inherently more complex than physical systems; you cannot visualize a large software system well enough before construction to understand all the consequences. So the initial design will have many problems. Those problems often do not surface until implementation. But the waterfall model does not accommodate large design changes at that point (for example, the designers may have moved on to other projects). Developers therefore patch problems without changing the overall design. The result is explosive growth in complexity.

Because of these issues, most software projects today use incremental approaches such as agile development: the initial design focuses on a small slice of overall functionality. That slice is designed, implemented, and evaluated. Problems in the original design are found and fixed; then more features are designed, implemented, and evaluated. Each iteration exposes problems in the existing design, which are fixed before the next set of features.

With this approach, initial design flaws can be corrected while the system is still small; later features benefit from experience gained while implementing earlier ones, so they tend to have fewer problems.

The incremental approach suits software because software is malleable and major design changes are possible during implementation. By contrast, major design changes are much harder for physical systems—it is not realistic to change the number of bridge piers halfway through construction.

Incremental development means software design is never finished. Design continues through the entire lifecycle of the system; developers must always think about design issues. Incremental development also means continuous redesign. The initial design of a system or component is rarely the best; experience teaches better approaches. As a software developer you should always look for opportunities to improve the design of the system you are building, and you should plan to spend some of your time on design improvements.

If developers must always think about design, and reducing complexity is the most important element of software design, then developers must always think about complexity. This book is about how you can use complexity as a guide to software design throughout its entire lifecycle.

This book has two overall goals. The first is to describe the nature of software complexity: what “complexity” means, why it matters, and how to recognize when a program has unnecessary complexity. The second, harder goal is to introduce approaches that minimize complexity during software development. Unfortunately there is no simple recipe for great software design. Instead I will present a set of fairly high-level, almost philosophical ideas—such as “classes should be deep” and “define errors out of existence.” These ideas cannot instantly tell you the best design, but you can use them to compare alternatives and to explore the design space.

## 1.1 How to use this book

Many of the design principles here are somewhat abstract, so they can be hard to understand without looking at real code. Finding examples is challenging: they must be small enough to fit in a book yet substantial enough to illustrate real system issues (if you find good examples, please send them to me). So the book alone may not be enough for learning how to apply the principles.

The best way to use this book is together with code review. When you read other people’s code, think about whether it fits the ideas discussed here and how they affect complexity. It is easier to see design problems in someone else’s code than in your own. You can use the red flags described here to spot problems and suggest improvements. Reviewing code also exposes you to new design approaches and programming techniques.

One of the best ways to improve design skill is to learn to recognize red flags: signs that a piece of code is probably more complex than it needs to be. Throughout the book I will point out red flags for important design issues; the most important ones are summarized at the end. You can use them while coding: when you see a red flag, stop and look for an alternative design that removes the problem. The first time you try this you may need to explore several alternatives before you find one that removes the red flag. Do not give up easily: the more alternatives you try before solving the problem, the more you learn. Over time you will see fewer red flags in your code and your designs will get cleaner. Your experience will also surface other red flags you can use to spot design problems (I would love to hear about those).

When applying ideas from this book, moderation and caution matter. Every rule has exceptions; every principle has limits. If you take any design idea to an extreme you will probably get into trouble. Good design balances conflicting ideas and methods. Several chapters include sections titled “Taking it too far,” describing how to recognize when you have gone too far.

Almost all examples in this book use Java or C++, and much of the discussion is about designing classes in object-oriented languages. But the ideas apply in other settings too. Almost everything said about methods applies equally to functions in non-object-oriented languages such as C. Design ideas also apply to modules other than classes, such as subsystems or network services.

With that background, let us look more closely at what causes complexity and how software systems can be simplified.
